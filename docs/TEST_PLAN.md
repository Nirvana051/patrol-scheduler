# 全流程测试方案（Gazebo 仿真 → 真机）

目标：在 Gazebo 里把「同步地图 → 任务航点 → 执行 → 检查 → 播报」整条链跑通并把参数调顺，真机只剩 ②③④ 与机头校准。
前提：机器人端本地服务（8761）在线——`make smoke` 里 ③④⑤⑥ 全部 ✅ 才开始。每一步都写了**通过标准**，不达标就停在那一步排查（`docs/OPERATIONS.md §7`）。

> 这套 Gazebo 与真狗共用一个 roscore：**全程不要点「启动设备 / 停止设备」**（上游 `04_verify_flow.py` 的警告：会把仿真的速度指令接到真狗上 / 杀掉真机节点）。只用「执行 / 停任务 / 急停」。

## 0. 前置（10 分钟）

0. 换机器/首次：`./bootstrap.sh --dev`（建隔离 venv + 按 `requirements.lock` 装依赖 + 自检），
   然后 `make test`（118 用例）与 `make docs-check` 都应全绿。**自检里那句「每个包都来自 venv 内部」
   必须是 ✅** —— 这台机器上 ROS 的 `PYTHONPATH` 会把 venv 里的包顶掉（见 HANDOFF §5.4 第 21 条）。
1. `make smoke`：鉴权、在线、`/position` 200（仿真自带定位）、地图 ≥1 张且有航点、`/task` 有 `active/terminal`、SSE 可连、HLS 可取。
2. 打开 http://127.0.0.1:8088 ，顶栏应为 **REAL**、在线 ●、定位就绪 ●、云端任务 IDLE。点「刷新状态」→ 前置检查全部 ✅。
3. 设置页：
   - 抓图源 `rtsp`（实测 3 s/帧；想快改 `hls`，0.8 s 但画面落后 2–3 s）。
   - VLM 先用 `mock`（`alternate`）把链路跑通，第 4 步再换真模型。
   - TTS 引擎 `edge`、汇出 `browser`；**在页面上点一下**解除浏览器自动播放限制（右上角 🔊 亮着）。
   - `SETTLE_SECONDS=3`、`LEG_TIMEOUT=300`、`NOT_STARTED_TIMEOUT` 先 40（仿真起步时间未知）。
4. 总览「抓一张全景」→ 能出图、分辩率 1280×640。

通过标准：以上无 ❌；事件页出现 `app_started`、`snapshot`。

## 1. 地图（5 分钟）

1. 地图页 → 对唯一那张真实地图点「同步」→ 提示同步 87 个航点（数字以实际为准）。
2. 画布上应看到航点、邻接边、机器人蓝色箭头落在某个航点附近；「连通块」应为 1（>1 说明拓扑断裂，执行时可能「不连通」）。
3. 路线预览：从机器人最近航点到一个远端航点「算路」→ 有路径、长度合理（相邻编号只差几十厘米，选彼此拉开的点）。

通过标准：87 点 / 1 个连通块 / 算路成功。

## 2. 第一轮：只为收集全景（15 分钟）

先不纠结角度范围——第一趟的目的是让机器人在每个点位各抓一张真实全景，之后用它们定范围。

1. 选 3 个彼此拉开的航点（如上游建议 `1, 20, 45`）。地图页点航点 →「添加为任务航点」，名字随意，prompt 填任意一句，角度范围先用默认 150°→210°，保存。
2. 任务规划 → 新建任务「采样」，加入这 3 个航点，**起始点**先留「自动」（想固定从某点起步就选那个航点），选项：稳定 3 s、每段超时 300 s、重试 1、返回起点 ✓、要求定位就绪 ✓ → 保存 →「路线」预览各段路径与总长 → 「执行」（确认框会提示真机会动）。
3. 执行监控里看：段 1 `已下发 → 导航中`（卡片显示「已过 k/n 点」）→ `已到达` → `检查中` → `完成`；每段完成出现一张检查卡片（带范围标注的全景 + 裁切 + mock 回答 + 播报，浏览器应念出来）。
4. 记录每段的下发/到达时刻（卡片上有）：这就是仿真里的起步与行走时间，用来定 `NOT_STARTED_TIMEOUT` 与 `LEG_TIMEOUT`。

通过标准：执行 `已完成`；3 张检查卡片都有全景与裁切；任务事件里既有系统事件（`leg_dispatched`…）也有云端事件（`waypoint_reached`、`task_completed`）且序号连续；机器人回到起点。
不通过时：`任务下发成功但机器人没有动` → 看 OPERATIONS §7；`不连通` → 换航点；一直 `导航中` 不到 → 看云端任务卡片的 `error_code`。

## 3. 用真实全景定范围与 prompt（20 分钟）

1. 打开每条检查卡片的全景（`…_pano.jpg`），确认画面里要检查的目标在哪一段方位；在任务航点编辑器里「上传」这张图作参考图，把两条黄线拖到目标两侧（留 5–10° 余量），保存。
2. prompt 写成**只能用是/不是回答**的问题，并点明目标：例如「画面中间的红色圆柱是否完整可见？」；答案模版：期望 `是`，三句播报写具体。再加一个期望「不是」的点（如「通道上是否有障碍物？」），验证不通过分支。
3. 每个航点点「试问 VLM（用参考图）」：mock 下看裁切图对不对；再看「将播报」句子是否是你想要的。
4. 再执行一次任务：这次检查卡片里的裁切应正好框住目标。

通过标准：每个点的裁切图里目标完整；播报句子与期望一致。

## 4. 换真 VLM（20 分钟）

1. 设置页 VLM 改 **`qwen`**（阿里 DashScope：地址留空、模型 `qwen3.5-flash`、填 `sk-…` 密钥）或 `openai_compat`（Ollama/vLLM，填 base_url + model）或 `anthropic`（填 key），保存。先 `make vlm` 命令行探一次，通了再往下。
2. 每个航点「试问 VLM（用参考图）」：看回答、原始 JSON、耗时；不对就改 prompt（更具体的目标描述、加"只看画面中间"），或把范围收窄，或勾「附整张全景」。
3. 再跑一趟任务；对每条检查点「判通过 / 判不通过」做人工复核；跑 3–5 趟后 `make eval`（用复核当标注算准确率、看误判清单）。

通过标准：真模型在参考图上的回答稳定；`make eval` 准确率达到你能接受的水平（先看 ≥ 90%）。

## 5. 故障与看护演练（仿真里安全，15 分钟）

| 演练 | 操作 | 期望 |
|------|------|------|
| 中止 | 导航中点「■ 中止」 | 执行 `已中止`，云端任务停下（总览云端任务卡片不再 active） |
| 跳过 | 导航中点「⏭ 跳过」 | 该段 `已跳过`，下一段从当前位置重规划 |
| 外部停任务 | 导航中点顶栏「停任务」 | 执行 `已中止`，原因「云端任务被外部停止」 |
| 现场抢控制权 | 让管理员在云端界面接管 | 下一段下发 409，事件 `leg_dispatch_409`，等待/重试后段失败 |
| 急停 | 顶栏「急停」→ 观察 → 「取消急停」 | 顶栏「急停中」红灯；遥测 `emergency_active=true`；取消后恢复。它是 20 Hz 停止指令，不是硬件急停 |
| 从失败段重跑 | 任一失败/中止的执行 | 右上「从『某航点』重跑剩余航点」→ 新执行只走剩余的 |
| 定时 | 任务「⏰ 定时」加每 N 分钟，「立即执行」 | 事件 `schedule_fired`；有执行在跑时再触发 → `schedule_skipped` |
| 进程重启 | 执行中重启调度系统 | 启动后残留执行被标为中止（`runs_reconciled`），机器人已被 DELETE /task 停下 |

### 5.1 真实云端上的演练结果（09-05）

| 演练 | 结果 |
|------|------|
| 中止 | DELETE /task 返回 200，但机器人**有时不停**（21:27 走到终点才停，21:42 则 1 s 内 `task_stopped`）。系统会核实 `stop_wait_seconds`，核实不了记红色事件并通知——此时用急停 |
| 顶栏停任务 | 云端 1 s 内发 `task_stopped`，执行标「被外部停止」 |
| 现场下发别的任务 | 云端**不发**新的 `task_started`；系统按到达事件的 `total` 与本段路径长度不一致识别为外部任务，3 s 内中止且不停对方任务 |
| 急停/取消 | `emergency_active` 随之变化，云端 `emergency` 事件双向到达；导航中急停：5–7 s 滑行后停住，任务不取消，取消急停后继续走完 |
| 控制权抢占 | 需管理员配合，未演练 |

## 5.5 实测参考值（09-05，Gazebo 机器人经真实云端）

| 量 | 实测 | 备注 |
|----|------|------|
| 行走速度 | ≈ 0.75–0.8 m/s，约 1.4 s 一个航点（航点间距 1.1 m） | 33 m 段 44.5 s，84 m 段 108 s |
| 下发 → 起点到达事件 | ≈ 0.25 s | 起点 `waypoint_reached` 与 `task_started` 同批到达 |
| 到点 → 检查完成 | 3.6–3.9 s | 抓帧 3.0 s（RTSP TCP）+ mock VLM + edge-tts 0.8 s，不含 3 s 稳定 |
| 全景分辨率 | 1280×640，15 fps | 画面随位姿实时变化 |
| 云端偶发 | nginx 层 HTML 502（约每几分钟一次） | 只记一条 warn，下一次对账正常 |

据此的默认值：`NOT_STARTED_TIMEOUT` 25–40 s 足够；`LEG_TIMEOUT` 按最长段 ×2；`SETTLE_SECONDS` 2–3 s。真狗速度可能不同，上真机后重测一遍。

## 6. 收尾与留档

- **不要停设备**（见开头）。导出一份 JSON 备份（设置 → 备份/迁移 → 导出）；`make backup`。
- 把 §2 记录的时间填回任务选项与设置：起步时间 → `NOT_STARTED_TIMEOUT`，最长一段 ×2 → `LEG_TIMEOUT`，抓帧耗时 + 停稳 → `SETTLE_SECONDS`。
- 真机上多做两件事：总览 ②③④ 初始化（`node_id` 用机器人真实所在航点），设置页「机头校准」（让机器人朝一个已知地标，把蓝线拖到该地标的列）。

## 每一步的证据在哪

执行监控（段时间戳、检查卡片、本次事件、CSV 导出）；任务事件页（云端 + 系统统一时间线）；总览「近 30 天按航点统计」；`data/logs/app.log`；`/api/health` 系统自检。
